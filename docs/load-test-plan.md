# Vestige 부하 테스트 계획

이 문서는 성능 개선 라운드의 규칙을 선언한다. 실행 방법은 3절과 `k6/run-journey.ps1`의 주석을 본다.

측정을 시작하기 전에 이 문서를 확정하고, 이후에는 결과가 나쁘다는 이유로 바꾸지 않는다.
기준을 바꾸면 이전 결과는 전부 폐기한다.

## 0. 도전 목표 (선언)

> **동일 장비에서 동시 사용자 5,000명이 실제 사용 패턴대로 앱을 쓰는 동안,
> 전 API가 p95 SLO(조회 100ms, 쓰기 200ms)와 오류율 0.1%를 지킨다.**

- 이 숫자는 SLO와 달리 "지켜야 하는 기준"이 아니라 **부수러 가는 벽**이다.
  도달하지 못해도 실패가 아니다 — 최종 도달치와 남은 병목 분석까지가 결과물이다.
- 도전 목표는 측정 결과를 보고 낮추지 않는다. 선언한 숫자는 끝까지 유지한다.
- **5,000명을 고른 이유는 측정으로 정했다.**
  - 시나리오를 하나로 합치고 think를 실제 사람 속도로 올린 뒤 5,000 VU가
    오류율 0%로 완주했다. 그 전에는 워밍업과 측정이 별도 시나리오라
    측정 시작 순간에 VU가 전부 새로 생성되어 첫 API로 몰렸다.
  - 시드가 계정 4,000개를 제공하므로 조회 VU 하나가 실제 사용자 하나에 대응한다.
    **환경 한계로 판단한다** — 앱, MySQL, k6, Prometheus, Grafana가 한 노트북에 있다.
  - 5,000 VU: 오류율 77%로 측정 불가. **원인은 아직 규명하지 않았다.**
    서버가 연결을 못 받은 것인지 생성기가 요청을 못 보낸 것인지 구분이 안 된다.
- 계정을 공유하면 작업 집합이 작아져 캐시 히트율이 비현실적으로 높아진다.

**오류율은 "무언가 깨졌다"만 말한다. 무엇이 깨졌는지는 별도로 규명해야 한다.**
높은 오류율을 곧바로 "생성기 한계"나 "서버 한계"로 단정하지 않는다.
5,000 실행에서 대부분의 API가 `p95 0ms + 오류율 100%`로 나왔는데, 이는
요청이 서버에 닿지 못했다는 뜻일 뿐 어느 쪽이 원인인지는 말해주지 않는다.

구분 기준:

| 지표 | 생성기 한계 | 서버 한계 |
|---|---|---|
| 생성기 머신 CPU | 80% 초과 | 여유 |
| `k6_http_req_blocked`, `k6_http_req_connecting` | 크다 | 작다 |
| Tomcat `connections_current` | 낮다 (요청이 안 옴) | max에 붙는다 |

이 셋을 보지 않고 원인을 적은 라운드는 기록하지 않는다.

### 측정 모델을 바꾼 이유와 그 대가 (2026-08-19 선언)

이전 계획은 **열린 모델**(도착률 고정)로 "초당 몇 건까지 견디나"를 쟀다.
지금은 **닫힌 모델**(VU 고정)로 "사용자 N명이 얼마나 기다리나"를 잰다.

바꾼 이유는 두 가지다.

1. 개선의 서사가 직관적이다. "800에서 1,100 req/s"보다 "같은 5,000명인데
   p95가 2.3초에서 180ms"가 읽는 사람에게 즉시 전달된다.
2. 실제 화면 흐름대로 API를 호출하므로 트래픽 비율에 근거가 생긴다.
   이전의 `조회 60 / 상세 20 / 탐색 10`은 임의의 가중치였다.

**대가: 이전 라운드 결과를 전부 폐기한다.**

- R0의 800 req/s는 도착률 기준 용량이라 이 정의로는 비교할 수 없다.
- 게다가 그 측정은 멀티파트 업로드 코드 기준이다. presigned 전환(PR #116)으로
  시스템 자체가 달라져 어차피 비교 대상이 아니다.
- 시드도 v2(1,000명)에서 v3(5,000명)로 바뀌었다.
- 따라서 **2026-08-19 이전의 모든 측정 결과는 폐기하고 baseline을 다시 잡는다.**

**닫힌 모델의 알려진 한계 (포폴 방법론 절에 명시할 것).**
서버가 멈추면 VU도 응답 대기로 함께 멈춰 느린 구간을 적게 샘플링한다
(coordinated omission). 따라서 여기서 나오는 p95는 실제보다 낙관적이다.
전후를 같은 VU 수에서 비교하면 편향이 양쪽에 똑같이 걸리므로 **개선 폭은
유효하지만 절대값은 낙관적**이라는 점을 결과에 병기한다.

## 1. 목표 정의

**판정 단위** = 동시 사용자 5,000명 고정 상태에서 **전 API가 SLO를 지키는가**.

- 처리율(req/s)은 입력이 아니라 **결과값**이다. 같은 VU에서 처리율이 오르면
  대기가 풀렸다는 뜻이다.
- 개선의 성과는 두 축으로 보고한다.
  1. **지연**: 같은 VU 5,000에서 API별 p95, p99가 얼마나 내려갔나
  2. **처리율**: 같은 VU 5,000에서 req/s와 세션 완료/s가 얼마나 올랐나
- 라운드 표에는 두 축을 함께 적는다. 하나만 좋아지는 경우가 있기 때문이다.

## 2. SLO

단일 출처는 [k6/lib/slo.js](../k6/lib/slo.js)다. 여기는 요약만 둔다.

| 분류 | p95 | p99 | 해당 API |
|---|---:|---:|---|
| 조회 | 100ms | 200ms | 지도 목록, 지도 상세, 마커, 추억 목록, 추억 상세, 캘린더, 내 정보, 초대 목록, 친구 목록 |
| 쓰기 | 200ms | 400ms | 텍스트 추억 생성, 추억 수정, 지도 생성, **업로드 발급, 업로드 완료** |
| 참고 | 없음 | 없음 | **S3 직접 PUT** |

- 오류율: **전체 및 API별 각각 0.1% 미만** (S3 직접 PUT 포함)
- check 성공률: 99.5% 초과

**업로드 지표 정의 (presigned 전환 완료, PR #116).**
업로드는 이제 서버 API 2개와 S3 직접 PUT 1개로 나뉜다.

1. **발급, 완료 API** — 쓰기 SLO(200ms) 적용. 서버 용량 판정에 들어간다.
2. **S3 직접 PUT** — 서버를 거치지 않는다. S3와 회선이 지배하는 값이므로
   지연 판정에서 제외하고 수치만 기록한다. 오류율은 건다.

p99를 함께 거는 이유: 커넥션 풀 대기, GC pause 같은 간헐 병목은 p95보다
p99에서 먼저 드러난다. 꼬리가 몸통의 2배를 넘으면 병목이 있다고 본다.

## 3. 테스트

측정 도구는 하나로 통일한다. 열린 모델 기준으로 만든 스크립트
(`mixed.js`, `capacity.js`, `upload.js`, `smoke.js`와 각 래퍼)는
판정 정의가 달라져 쓸 수 없으므로 **2026-08-19에 전부 삭제했다.**
옛 결과물(`results-archive/`)도 같은 이유로 삭제했다.

| 테스트 | 실행 | 목적 |
|---|---|---|
| **여정 부하** | `.\k6\run-journey.ps1 -Vus 5000` | **판정은 여기서만 한다.** 업로드 포함 |
| 지속 (soak) | `-Vus 5000 -Duration 20m` | 누수, 힙 증가, GC 폭주 확인 |

**래퍼 없이 `k6 run`으로 직접 실행하지 않는다.** 래퍼가 설정하는
`K6_PROMETHEUS_RW_TREND_STATS`가 없으면 k6는 p(99)만 전송하고
Grafana의 p95 패널이 전부 비어 있게 된다.

전제 검증(시드, 권한, 상태코드)은 별도 스모크 스크립트 없이
여정 부하의 **워밍업 60초 구간**으로 대신한다. 워밍업에서 오류율이 튀면
측정 구간에 들어가기 전에 중단하고 원인을 먼저 잡는다.

## 4. 부하 조건

**VU는 5,000으로 고정한다.** 다른 값으로 돌린 결과는 라운드 표에 적지 않는다.

- 모든 라운드는 **워밍업 60s + 측정 2m**을 유지한다. 시간을 줄여 빨리 돌린
  결과는 탐색용으로만 쓰고 기록하지 않는다.

### think time 규칙

닫힌 모델의 부하량은 VU 수와 think time이 함께 결정한다.

```
처리율 = VU 수 x 세션당 호출수 / (응답시간 + think time 총합)
```

- **`THINK=1.0`(실제 사람 속도)을 기본으로 고정한다.** 배율을 낮추면
  "가속 사용자" 모델이 되어 동시 사용자 수의 의미가 흐려진다.
- 5,000 VU로 서버가 포화되지 않게 되면(개선이 진행되면) **VU를 올리되 think는 낮추지 않는다.** VU를 바꾸면 도전 목표가 달라지므로 목표를 다시
  선언하고 이전 라운드를 폐기한다.
- think 조정은 최후 수단이다. 쓰면 결과 md와 포폴에 그 사실을 명시한다.

### 실행 무효 판정

닫힌 모델에는 `dropped_iterations`가 없다(도착률 목표가 없으므로 항상 0).
대신 아래를 확인한다.

- **생성기 머신 CPU 80% 초과 → 무효.** VU 5,000은 생성기 부담이 크다.
- `k6_vus`가 설정값에서 벗어나면 무효.
- 오류율이 SLO를 넘으면 그 실행은 지연 판정을 하지 않는다. 고장부터 고친다.

## 5. 라운드 프로토콜

한 라운드 = 측정 → 병목 규명 → **수정 1개** → 재측정.

1. **한 라운드에 수정은 하나만.** 두 개를 같이 고치면 기여도를 영원히 말할 수 없다.
2. **파라미터 스윕은 수정 하나로 센다.** 커넥션 풀을 10/20/30/50/100으로
   쓸어보는 건 수정 5개가 아니라 변수 하나를 여러 값으로 관찰한 것이다.
   오히려 전후 비교보다 강한 근거가 되므로 권장한다.
   - 단, **두 노브를 동시에 돌리지 않는다.** 풀 스윕은 버퍼풀 고정,
     버퍼풀 스윕은 풀 고정.
   - 스윕 결과는 곡선으로 남긴다. 최적점과 꺾이는 지점이 포폴의 핵심 그래프다.
3. 커밋 해시를 결과에 기록한다. `-dirty`면 그 사실을 병기하되 측정을 막지는 않는다.
4. 병목 규명은 같은 부하에서 Grafana로 한다. 근거 없이 "느려서 고쳤다"는
   라운드는 기록하지 않는다. 최소 한 개의 시계열(hikaricp pending,
   tomcat busy threads, CPU, GC 등)을 근거로 남긴다.
5. **라운드 간 데이터 상태를 복원한다.** (7절)
6. 환경은 라운드 내내 고정한다. (8절)

### 라운드 기록 형식

```
① 증상   Grafana 캡처 (어느 지표가 먼저 무너졌나)
② 가설   "병목은 ~다"
③ 스윕   값을 바꿔가며 측정
④ 곡선   최적점과 꺾이는 지점
⑤ 선택   확정값과 그 이유 + 재측정
```

④가 있고 없고가 포폴의 급을 가른다. 대부분의 성능 글에는 ①②⑤만 있다.

## 6. 트래픽 구성

`k6/journey.js`의 여정 정의를 따른다. 비율은 임의의 가중치가 아니라
**"앱을 100번 열었을 때 각 화면을 몇 번 보는가"**에서 유도했다.
화면 하나가 API 여러 개를 부르므로(지도 상세 = 3개) 비율은 여정을 정하면
자동으로 결정된다.

| 동작 | 100세션당 | 호출 API |
|---|---:|---|
| 홈 진입 | 100 | 지도 목록 |
| 알림 확인 | 20 | 초대 목록 |
| 지도 열기 | 95 | 지도 상세 + 마커 + 추억 목록 (3개) |
| 추억 열람 | 190 | 추억 상세 |
| 목록 스크롤 | 50 | 추억 목록 |
| 캘린더 | 15 | 캘린더 |
| 마이페이지 | 10 | 내 정보 |
| 친구 목록 | 8 | 친구 목록 |
| 추억 작성 (텍스트) | 8 | 추억 생성 |
| 추억 작성 (파일) | 12 | 발급 + S3 PUT x4 + 완료 |
| 추억 수정 | 2 | 추억 수정 |
| 지도 생성 | 10 | 지도 생성 |

세션당 약 7.1회 호출, **읽기 95.5% / 쓰기 4.5%**.

**호출 비율과 부하 비율은 다르다.** 캘린더는 호출의 2.1%지만 건당 비용이
다른 조회의 몇 배라 서버 시간 점유율은 훨씬 크다. 개선 대상 선정은 호출
비율이 아니라 `API별 p95 x 호출수`로 판단한다.

### 업로드 포함 여부

`journey.js`의 기본값은 **업로드 포함**이다.

멀티파트 시절에는 6MB가 서버를 통과해 1 req/s에서도 SLO를 깨뜨렸고, 그래서
별도 트랙으로 격리했다. presigned로 바뀐 뒤에는 서버가 작은 JSON 두 개
(발급, 완료)만 처리하고 파일은 k6에서 S3로 직접 간다. **격리할 이유가 없어졌다.**

- 도전 목표의 "전 API"에는 발급과 완료가 포함되므로 기본으로 켜는 것이 맞다.
- `PUT_s3_direct`가 느리면 서버가 아니라 **생성기 업링크가 병목**이다.
  그때만 `-NoUpload`로 빼고, 뺀 조건을 결과 md에 병기한다.

### 수정 부하는 멱등이다

`editMemory`는 memoryDate와 category를 시드와 같은 값으로 계산해 보낸다
(`helpers.js`의 `seedMemoryDate` 참고). 시드 분포가 라운드마다 훼손되면
캘린더(year=2024)의 대상 행 수가 줄어 아무것도 안 고쳐도 저절로 빨라진다.

## 7. 데이터 통제

- 시드: `backend/scripts/load-test-seed.sql` **v3**
  - users 5,000 / maps 5,000 / map_members 14,000
  - **memories 290,000 / media_files 1,160,000** / friendships 25,000
  - 헤비 지도(1~200)는 500개씩, 라이트 지도(201~4,000)는 50개씩.
    마커 조회가 지도 전체를 반환하므로 헤비 지도 기준 응답 500행이
    무거운 조회 역할을 한다.
  - 계정 배정: 조회 1~4,000 / 쓰기 4,001~4,700 / 업로드 4,701~4,900 /
    지도생성 4,901~5,000. 쓰기 대상은 추억이 0개인 빈 지도라 조회 대상
    지도의 추억 수가 실행 중에 변하지 않는다.
  - PENDING 초대 4,000건을 포함한다. 없으면 `GET /api/map/invitations`가
    항상 빈 배열이라 그 API를 측정할 수 없다.
  - **v3 적용 이전(2026-08-19 이전)의 측정 결과는 전부 폐기한다.**
- 라운드 반복 시 k6 teardown은 쓰지 않는다(서버에 부하를 다시 걸고 오래 걸린다).
  `journey.js`는 기본으로 정리하지 않으며, 라운드 사이에
  [load-test-cleanup.sql](../backend/scripts/load-test-cleanup.sql)을 실행한다.
  검증 SELECT가 시드 원본 수치와 일치해야 복원된 것이다.
- 정리 시점: 라운드가 바뀔 때, 무효 실행 뒤.
- **매 실행 전후로 [perf-db-snapshot.sql](../backend/scripts/perf-db-snapshot.sql)을 실행한다.**
  인덱스 라운드만이 아니라 전 라운드에 적용한다. `Innodb_buffer_pool_reads` 델타(x 16KB)를
  결과에 적어야 "버퍼풀이 데워진 상태였나"를 사후에 판별할 수 있다.
  - 2026-08-20에 이걸 안 해서 라운드 하나를 폐기했다. 같은 코드, 같은 설정인데
    처리량이 2.8배 차이 났는데 원인을 확정하지 못했다 (10절 시도 로그 3번).
  - **`OPTIMIZE TABLE`이나 시드 재생성 직후에는 측정하지 않는다.** 버퍼풀이 비워진다.
    최소 한 번 워밍업 실행을 버리고 그 다음부터 기록한다.
- S3 객체는 `test/` prefix의 Lifecycle 규칙이 정리한다. `S3_KEY_PREFIX=test/`
  설정을 매 실행 전에 확인한다.
- 캐시를 도입한 라운드부터는 매 실행 전 Redis를 비우고(`redis-cli FLUSHALL`)
  워밍업 60s 동안 채워지게 한다. cold와 warm이 섞이면 비교가 무너진다.

## 8. 환경 통제

- 앱: **IntelliJ 로컬 실행**, 힙은 로컬 기본값, G1GC (`AppMode=IntelliJ-local-C2`)
  - **힙을 운영(EC2 프리티어 1GB)에 맞추지 않는다.** 이 머신의 JVM 기본값
    (물리 메모리의 1/4, 약 16GB)을 그대로 쓴다. 라운드 간 상대 비교가 목적이고,
    절대 수치는 어차피 이 머신 기준으로만 주장하기 때문이다.
    - **한계로 기록한다**: 힙이 넉넉해 GC 압력이 운영보다 훨씬 낮다.
      GC 관련 개선의 효과는 이 환경에서 과소평가된다.
  - **JIT은 C2까지 켠다.** IntelliJ 실행 구성의 "Enable launch optimization"을
    해제해 `-XX:TieredStopAtLevel=1`을 제거한다. 이 옵션은 C1에서 컴파일을
    멈춰 운영(`java -jar`)에 존재하지 않는 성능을 측정하게 만든다.
    - 워밍업 60s는 C2 승격에 필요한 반복 횟수를 확보하는 역할도 겸한다.
  - Docker 격리를 검토했으나 채택하지 않았다. 대신 **한계로 기록한다**:
    IDE 실행은 다른 프로세스와 CPU를 나눠 쓰므로 라운드 간 노이즈가 크다.
    실행 중 다른 작업을 하지 않는 것으로 통제한다.
    - 실측: 백그라운드 프로그램을 정리하니 처리량이 187 to 322 req/s로 올랐다(2026-08-19).
  - 전 라운드 동일 방식을 유지한다. 바꾸면 그 시점까지의 라운드 표를 폐기한다.
- DB: local mysql8, 시드 동일 (`DbMode=local-mysql8`)
- **생성기와 서버가 같은 머신이다.** 2,000 VU에서 생성기가 먼저 포화되는 것을 실측했다. k6가 CPU를 상당히 쓰므로,
  서버 CPU 수치를 읽을 때 이 점을 감안한다. 매 실행마다 k6 프로세스 CPU를
  함께 기록한다.

### DB 환경 기록 — InnoDB 버퍼풀 (필수)

시드 v3의 전제는 **"데이터가 버퍼풀보다 크다"**는 것이다. 그런데
`innodb_buffer_pool_size`는 로컬 MySQL 설정이라 git 밖에 있고, 이 값이
바뀌면 모든 라운드 비교가 무효가 된다. 따라서 매 실행마다 기록한다.

- **자동 기록**: `$env:MYSQL_PWD`를 설정해두면 래퍼가 실행 직전에
  읽기 전용 SELECT 1개로 조회해 결과 md에 남긴다 (`k6/lib/db-env.ps1`).
  미설정 시 `unknown`으로 기록되고 측정은 그대로 진행된다.
- 시드 SQL 마지막 쿼리도 같은 값을 출력한다.
- **버퍼풀은 기본값(128MB)을 그대로 쓴다.** 배율을 원하는 구간에 맞추려고
  이 값을 미리 조정하지 않는다. 그건 측정 조건을 결과에 맞추는 행동이고,
  이 문서 서두의 원칙을 정면으로 위반한다.
- **배율은 판정 기준이 아니라 기록 항목이다.** 측정이 어떤 조건에서 이뤄졌는지를
  서술하는 값이며, 라운드를 무효로 만들지 않는다.
- **해석에만 쓴다**: `DB 크기 / 버퍼풀`
  - **< 1.0** → 데이터가 전부 메모리에 올라가 디스크 I/O가 거의 없다.
    이 조건에서 인덱스 라운드의 개선 폭이 작게 나와도 **"인덱스가 효과 없다"로
    결론짓지 않는다.** 조건을 결과에 병기하고, 그 자체를 발견으로 기록한다.
  - **1.5 ~ 3.0** → 디스크 I/O가 충분히 발생해 인덱스 효과가 잘 드러나는 구간.
- **버퍼풀 크기 자체는 별도 튜닝 라운드의 대상이다.** 128 / 256 / 512MB 스윕으로
  히트율과 지연 곡선을 그린다. baseline을 위해 미리 맞추는 것과, 개선 후보로
  실험하는 것은 다르다. 후자만 한다.
- **v3 기준선**: 버퍼풀 128MB(기본값) / DB 206.2MB / 배율 1.61 (2026-08-19 실측).

- **인덱스 라운드 주의**: 인덱스를 추가하면 `index_length`가 늘어 배율이 커진다.
  "인덱스로 읽을 행이 줄어든 효과"와 "캐시 경쟁이 심해진 효과"가 섞이므로,
  전후로 [perf-db-snapshot.sql](../backend/scripts/perf-db-snapshot.sql)을 실행해
  `Innodb_buffer_pool_reads` 델타(x 16KB = 디스크 읽기량)와 히트율을 함께 기록한다.
  - 이 카운터는 서버 시작 이후 누적이며 `FLUSH STATUS`로 리셋되지 않는다.
    반드시 **실행 전후 차이**로 본다. 누적 히트율은 현재 상태를 나타내지 않는다.
- 절대 수치는 이 머신 기준의 상대 비교로만 주장한다.

## 9. 개선 후보 백로그

라운드 순서는 이 표가 아니라 **측정이 정한다.** baseline에서 먼저 무너지는
지표부터 잡는다. 코드 근거는 착수 전에 재확인한다.

| 후보 | 코드 위치 | 근거 |
|---|---|---|
| HikariCP 풀 크기 + OSIV off | `application.yml` | `maximum-pool-size`, `open-in-view` 미설정 → 풀 10 기본, OSIV 기본 true. Tomcat 200 스레드가 커넥션 10개를 경쟁하고, 커넥션이 응답 직렬화까지 점유된다 |
| 캘린더 쿼리 인덱스 | `MemoryRepository.findAllByUserIdAndYear` | `YEAR(m.memoryDate) = :year` — 컬럼에 함수를 씌워 인덱스를 못 탄다. `BETWEEN` + `(map_id, memory_date)` 복합 인덱스 |
| 마커 DTO 프로젝션 | `MemoryServiceImpl.getMemoryMarkers` | 헤비 지도 500행 엔티티 전체를 로딩한 뒤 6개 필드만 쓴다. 커버링 인덱스 + 프로젝션 |
| 썸네일 조회 축소 | `MediaFileRepository.findByMemoryIdIn` | 추억당 미디어 4행을 전부 읽는다. `type=IMAGE` + `MIN(display_order)`로 1/4 |
| 권한 검증 캐시 | 전 조회 API | `@EnableCaching` 부재. 모든 조회가 `findByMap_MapIdAndUser_UserId`를 매번 실행한다. 멤버십은 거의 불변 |
| 초대 목록 N+1 | `MapServiceImpl.getInvitationList` | DTO 변환에서 지도와 초대자를 건당 조회 (1 + 1 + 2N) |
| 서명 URL 응답 크기 | 전 조회 API | presigned GET URL이 평문 URL의 5배 길이다. 캘린더는 건당 150개 이상 붙는다. `server.compression.enabled` 검토 |
| 목록 ORDER BY 부재 | `MemoryRepository.findByMap_MapId` | 정렬이 없어 페이지 간 중복, 누락이 가능하다. 기능 버그이자 재현성 문제 |
| InnoDB 버퍼풀 크기 | MySQL `my.ini` | 기본 128MB. 128 / 256 / 512 스윕으로 히트율과 지연 곡선을 그린다. 데이터가 206MB라 메모리에 다 안 올라가는 상태에서 시작한다 |

## 10. 기록 — 시도 로그와 라운드 표

### 시도 로그 (성공, 실패, 무효 전부 기록)

"한계 극복"의 증거는 성공 목록이 아니라 시도의 총량이다. **실패한 실험도
반드시 기록한다** — 단, 실패를 연출하지 않는다. 진짜 가설을 세우고 진짜로
실험한 것만 적는다.

| # | 가설 | 시도 | 결과 | 수치 | 배운 것 |
|---|---|---|---|---|---|
| 1 | OSIV가 커넥션을 직렬화까지 점유한다 | `open-in-view: false` | **음성** | 점유 시간 변화 없음 | Hibernate 6은 트랜잭션 종료 시 커넥션을 반납한다. OSIV 비용은 뷰 계층 지연 로딩이 있을 때만 발생하는데, DTO가 엔티티 참조 대신 값을 복사해 보관하므로(`MapInvitationDto.from()`) 해당이 없다. 유명한 안티패턴이 이 코드베이스에는 적용되지 않았다 |
| 2 | 측정값이 실행마다 흔들린다 | 같은 조건에서 반복 측정 | **환경 요인 규명** | 187 to 322 req/s | 백그라운드 프로그램 정리만으로 처리량 73% 차이. 유휴 상태 CPU 15.2%가 측정을 왜곡하고 있었다 |

> 동시 사용자 5,000명이 실제 사용 패턴대로 앱을 쓰는 동안 전 API가

> N번의 개선으로 조회 p95 C ms, 처리율 D req/s까지 도달.
